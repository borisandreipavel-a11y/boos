# Notes for whoever works on this kernel next

This folder holds what the code cannot say for itself: the order things must happen in, facts about the hardware, known limits, and how to check that the kernel still works. It is written for AI agents and people who pick the project up cold.

**Keep it true.** When code changes, change the matching note in the same change. A note that disagrees with the code is worse than no note. Record what was tested and what was not, and never write "tested" for something that was only compiled.

## What this is

A from-scratch kernel for x86-64 PCs, written in Rust. It is a UEFI application: the firmware loads it directly and there is no separate bootloader. It runs in QEMU and has never run on real hardware.

Today it starts, takes the machine over from the firmware, reports processor failures, listens to the timer and the keyboard, manages memory (frames, its own page tables, a heap), runs several tasks that take turns under the timer and can wait without using the processor, and finds and sets up its network card. A network stack runs in a task of its own and gets the kernel a network address. It can get random numbers from the processor and read the date from the clock chip. With all of that it fetches one web page at startup over an encrypted link: the site proves who it is with a certificate, which the kernel checks, and the kernel prints how the page begins. It can also run a small program that is not part of it, an app, locked in a box: the app gets a block of memory of its own and can touch nothing else. An app can ask the kernel for two things so far: to print a text, and to show a text on the screen. The kernel also carries a far bigger program for the box, an interpreter for the language Lua, in which apps are going to be written as text, as scripts. At startup it sees that the box would take the interpreter and has it run one script written by hand, which prints a line and shows a text on the screen. It can also write a text the way JSON wants it and find a text in a piece of JSON, the form that services on the internet speak, with code of its own; a check at startup shows that it does. It can lock a secret with a password, so that only someone who knows the password can read it back: the password is turned into a key in 600,000 rounds, and a check at startup shows that the locking gives published values and what another implementation gives. It knows where the screen's memory is and how large the screen is, because it asks the firmware before the takeover, and it can paint filled rectangles and write text there, with letters whose shapes were drawn by hand for it. Everything it says is shown there too, since a PC may have no serial port: while it starts its lines cover the whole screen, one below the other; F1 shows them again later; and when it stops on a failure, the screen turns red and says why. Once it has started it fills the screen with one colour and writes one sentence, and an app's text appears in a box in the middle of the screen. The app only says which text; the kernel decides how the box looks. Along the bottom of the screen is a chat box: what is typed on the keyboard appears there, small letters and with Shift capitals and the second signs of the keys, Backspace takes a sign away, and Enter sends the line. One line, `key`, makes it ask for a secret instead: what is typed then shows as stars, is kept in memory only, and goes neither to the terminal nor to the disk. Every other line, but `setup`, goes to a model through its provider over the encrypted link, with the secret as the key: the chat box leaves that as an errand for the network's task, which alone may use the network, and shows the answer when it comes (see below). It also finds the controller that the machine's disks are plugged into, sets it up, asks the first disk for its name and size, reads the list that says how the disk is divided into parts, and finds the part that is its own. It writes only inside that part. There it keeps a notebook: things kept under a name, each written as a new entry behind the last, so that nothing already written is ever changed. The first thing kept is the last line that was sent in the chat box, which the kernel says again at its next start. The person's name is kept there too: at a start where the notebook holds none, the kernel asks the person at the machine what to call them, puts the answer in front of their lines in place of `You`, and greets them by it at every later start. After the name it asks for the model's key and a password, and keeps the key there locked with the password; every later start asks for the password, which unlocks the key, so that lines go to the model without the key being typed again. The line `setup` asks both again. There are four looks, sets of colours for everything on the screen: the questions the kernel asks at a start end with one that lists them, until it has been answered once, and after `setup`, which first brings back the first look; the whole screen is painted at once in the one whose number is typed, and Enter keeps it there for later starts. It also keeps a count of its own starts there, which goes up by one at every start.

Every line typed in the chat box, but `key` and `setup`, goes to the model with a list of tools, the things the kernel can do for it; the model answers in words, or asks for a tool: a new app, a kept app run again, another look, or another page of the panel of apps. An app is asked for in plain words, such as `I would like a dice to roll`: the model asks for a new app with a short request, and is then asked to write that app as a Lua script, with a fixed text that tells it how an app for this kernel is written. The kernel checks the script that comes back, shows it in the terminal, line by line, and runs it once in the box: what the app shows appears in the box in the middle of the screen, and the chat box says how the run went. An app that ran to its end is kept in the notebook, its script and the request it was made for, a script longer than one entry in several, and a panel near the top left of the screen lists the kept apps, five a page, also after the machine was switched off and on again. A kept app runs again when the model picks it, without being written anew.

Outside `src/`:

- `vendor/` holds copies of seven crates that were not written for this kernel: smoltcp, the network stack, and heapless, which it needs; rustls, which speaks TLS, rustls-webpki, which checks certificates, and num-traits, which the arithmetic of encryption needs; wasmparser, which reads and checks an app's program, and libm, arithmetic for numbers with a point, both needed by wasmi, which runs apps. `vendor/README.md` says where they came from and what was changed. Their text is other people's and does not follow the conventions below.
- `interpreter/` is a program of its own, not part of the kernel: the interpreter for Lua. It has its own `Cargo.toml`, `Cargo.lock`, settings (`.cargo/config.toml`) and one source file, and is built for WebAssembly into one file, which the kernel's build reads in. It has to be built before the kernel. See [interpreter.md](interpreter.md).
- `password-key/` is a crate of this project's own, written for the kernel: `password_key`, which turns a password into a key in many rounds. It is a crate of its own only so that cargo builds it to run fast, like the outside crates; the kernel's own code is built the plain way. It has its own `Cargo.toml` and one source file, and no `Cargo.lock`: the kernel's lists it. See [lock.md](lock.md).
- `Cargo.toml` names thirteen dependencies, smoltcp, ten crates for encryption, wasmi, and the project's own `password-key`, and points cargo at the copies. `Cargo.lock` lists 79 crates besides the kernel; 69 of them are compiled.
- `lock.rs` uses the crate `password-key`, `chacha20poly1305`, `random.rs`, `secret.rs` (for `wipe` and the longest secret) and `lock_values.rs`.

- `.cargo/config.toml` sets the build target to `x86_64-unknown-uefi`, and tells the crates for encryption to use their plain code; see [encryption.md](encryption.md).
- `run.bat` builds the interpreter and then the kernel, copies the kernel to `esp\EFI\BOOT\BOOTX64.EFI` (where the firmware looks) and starts QEMU with a processor that can make random numbers, a virtio network card on QEMU's built-in network, and a disk controller with one disk, which is the file `disk.img`. It makes that file the first time and has `make-disk.ps1` divide it into parts.
- `make-disk.ps1` divides a new, empty disk file into parts, with one part for the kernel; see [disk.md](disk.md). It is written in PowerShell, which comes with Windows.
- `run-boot-disk.bat` does what `run.bat` does, but starts QEMU from the boot disk `boot.img` instead of the `esp` folder: it builds both, has `make-boot-disk.ps1` make the disk file the first time or write its start part again with the new kernel, and starts QEMU with the file on its AHCI controller and no folder. See [disk.md](disk.md), "The boot disk".
- `make-boot-disk.ps1` makes the boot disk: one disk file with a FAT32 start part that holds the kernel, written byte by byte, and boos's own part after it; see [disk.md](disk.md). For a disk made before it writes only the start part again.
- `README.md` in the project's root is the front page for a visitor: what the project is for, what the kernel does today, what a start looks like, how to run it, and where the outside code comes from. It repeats, shortly, what these notes say, and some of the lines a boot prints. When the kernel's abilities, its boot lines or the way to run it change, change it too.
- `test-tools/` holds the scripts that build, boot and check the kernel in QEMU, `.github/workflows/build.yml` has GitHub build it for every pull request, and `.github/workflows/boot-tests.yml` has GitHub boot it there and run the tests; see [testing.md](testing.md).
- `release/` holds what a release of the boot disk needs: `make_release.py`, which makes its files, `make_notices.py`, which makes the notices that go with it, `release-text.md`, the release's text, and in `notices/` the licence texts of the crates that hold none. `.github/workflows/release.yml`, started by hand, has GitHub make a draft release from `master`, with the steps in `.github/actions/release-files/`; see [release.md](release.md).
- Not in the repository: `esp/`, `target/` and `interpreter/target/` (build output), `edk2-x86_64-code.fd` (QEMU's UEFI firmware, copied from QEMU's `share` folder) and `disk.img` (the machine's disk, which holds what was stored on it).
- `LICENSE-MIT` and `LICENSE-APACHE` are the two licences of the project's own code: whoever uses it chooses either. The outside code keeps its own: the copies in `vendor/` hold their licence files (see `vendor/README.md`), and the notices of the interpreter for Lua are in [interpreter.md](interpreter.md).

## Conventions

The code is written to be readable without a background in kernels: plain words, small files, every unusual step explained. Follow these, so the next change looks like the last one.

**Rust and dependencies**

- Stable Rust, edition 2024 (hence `#[unsafe(no_mangle)]` and `#[unsafe(naked)]`), `#![no_std]`, `#![no_main]`.
- Four pieces of outside code: smoltcp, the network stack, with the seven crates it needs; rustls, the TLS library, with the crates that do the arithmetic of encryption (52 compiled crates); wasmi, which runs apps, with the seven crates it needs; and omnilua, an interpreter for Lua, with the seven crates it needs. The first three are compiled into the kernel. omnilua is not: it is compiled into the interpreter, a program the kernel carries and runs in the box. Seven crates are kept as copies in `vendor/`; the others are fetched from crates.io the first time the kernel is built. Everything else is written for this kernel. `core` and `alloc` ship with Rust. Ask the owner before adding any dependency or tool.
- **The outside crates are built optimized, and the kernel's own code is not.** `Cargo.toml` says so in its last lines (`[profile.dev.package."*"]`, `opt-level = 2`), which reach every crate that is not the kernel itself, the copies in `vendor/` included, and the one crate of the project's own, `password-key/`, which is a crate of its own for exactly that reason. The outside code does the heavy work, the arithmetic of encryption and carrying out apps step by step, and built plain it was 2 to 25 times slower, depending on the work; the rounds of `password-key` were 16 times slower. The kernel's own code stays plain: it builds quickly, and it is the easiest to follow when something goes wrong. The compiler's checks for a number too large for its type stay on for all of it: a small crate built under the same lines was looked into, and the stop for a sum too large was in its built file, where a control with the checks switched off had none. The interpreter is a separate build with settings of its own; see [interpreter.md](interpreter.md).
- No crate may run a build script. The building computer refuses to run programs that were compiled a moment ago (see `vendor/README.md`), so a crate that has one can only come in as a copy with the script taken out. A macro crate, which the compiler loads as a piece of program during the build, has never been tried on such a computer: none is in use, and before taking one in, stop and ask.
- The `x86_64-unknown-uefi` target has no SSE (it uses soft-float), so code never touches the SSE registers. Several pieces rely on that; see [interrupts.md](interrupts.md). The kernel also tells the processor to refuse SSE instructions, so outside code that tried to use them stops with a report; see [encryption.md](encryption.md).

**Words**

- Names and comments use plain words. A device "signal" is an interrupt. A processor "failure" is an exception. A "frame" is 4096 bytes of real memory. A "pile" is a stack of free things. A table has "lines".
- The hardware's own name appears once, in brackets, where the thing is introduced: segment table (GDT), interrupt table (IDT), interrupt controller (PIC), timer (PIT).
- Comments sit above the thing they explain and say why, not only what. Magic numbers sent to devices get a comment in quotes saying what they tell the device.

**Structure**

- One topic per file. `main.rs` holds only the startup order, the main loop and the panic handler.
- Each file starts with a `//!` header: what the file is for and which note covers it.
- Functions keep their topic in the name (`serial_setup`, `frame_take`) and are imported by name, so a call reads `frame_take()`, not `frames::take()`.
- A macro must be defined above the place that uses it, in the same file. `fault_entry!` lives with `FAULTS`, `device_entry!` lives with `load_interrupt_table`, and `switch_entry!` lives in `tasks.rs` with the two entries it produces. Do not split them apart.
- Only what another file needs is `pub`.

**Shared values**

- A value shared between a signal handler and other code is an atomic from `core::sync::atomic`, used with `Ordering::Relaxed`.
- Other global state is a `static mut`, read and written by value inside `unsafe`. Edition 2024 refuses references to a `static mut`; use `&raw` when an address is needed. Six files depart from "by value": the chat box keeps two lists that grow, which cannot be copied in and out, so `chat.rs` has two small functions that hand them out through their addresses, and a third for the room a secret is typed into; `onboarding.rs` has two, for the person's name, a text that grows, and for the locked key read from the notebook; `secret.rs` reaches the rooms where the secret and a key being tried are kept in the same way, so that no copy of either is made there (the one file that borrows them makes one, and wipes it); `notebook.rs` has one such function for its list of names, and `apps_kept.rs` one for its list of kept apps; and `errand.rs` reaches the errand and the answer that wait there in the same way, with device signals off, because two tasks touch them. The rule that goes with them is written above them and in [chat.md](chat.md).
- Several tasks run at once, and a switch can happen between any two instructions. State that more than one task changes is changed with device signals off: `let were_on = signals_off(); ... signals_back(were_on);`. See [tasks.md](tasks.md).
- Signal handlers only count or store. They never print.

**Output**

- Everything the kernel says goes through the serial port: `serial_print("...")` or `write!(serial, "...")` with `let mut serial = Serial;`. Lines end in `\r\n`. `serial_print` also keeps every line for the screen, where the kernel's lines show while the machine starts, after F1, and when it stops (see "The kernel's lines" in [screen.md](screen.md)), so nothing that should not be seen may be printed. What is said in the chat box is on the screen as well, and is repeated through the serial port as whole lines.
- From a task, build the line first and send it in one go, `serial_print(&format!(...))`, so another task's line cannot land in the middle of it. Lines that must stay together, such as the report about a fetched page, are built as one text and sent in one go too.
- Text that comes from outside the kernel, such as a web page, is never printed as it arrived. Only plain letters, digits and signs pass; see `plain_sign` in `page.rs`.
